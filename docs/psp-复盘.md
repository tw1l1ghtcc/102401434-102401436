## 五、复盘结论（Postmortem）

**做对了什么**

1. **先把框架约定对齐**：字段名、存储键（`campus-lost-found-items`）、class 名全部沿用对方那半，
   所以两人合起来不用改数据、不用迁移。
2. **把"判断"和"画界面"拆开**：`logic.js` 是纯函数（不碰 DOM、不碰 localStorage），
   所以 35 条单元用例可以脱离浏览器直接跑；`render.js` 只负责写 DOM。
3. **测试当验收用**：端到端脚本会真的跑 `index.html`、用真事件走完 7 屏，
   而且断言的是"文案逐字一致"，所以它同时承担了"功能对不对"和"跟原型像不像"两件事。
4. **差异写进文档**：三处与原型不一致的地方（分类补齐六类、首页分类原地筛选、原型自身矛盾）
   都写在 README 第三节，答辩时不会被问住。

**踩到的坑**

1. **原型自己前后不一致**：01-首页把「蓝色校园卡」画成"寻找中"，03/04 屏却画成"招领｜待认领"；
   两个首页标签的状态帧内容还完全一样。→ 教训：**原型不等于规格**，动手前要先把矛盾挑出来定口径。
2. **筛选状态串味**：点分类时顺手把条件写进了搜索状态，导致之后搜「校园卡」出现 0 条。
   → 教训：**不同入口的筛选状态要分开**，别共用一份可变状态。
3. **测试脚本自己也会错**：端到端一共报出 4 次失败，其中 3 次是我脚本的预期写错（async 没 await、
   日期已预填所以只报 5 项、分类清单改成六类后没同步）。→ 教训：测试失败先分辨是"代码错"还是"预期错"。

**改进方向**

1. 下次**先定数据字典**（字段、状态机、分类枚举），再动页面 —— 这次的分类清单就是边做边补的，返工了一次。
2. **把提交节奏提前**：这半一开始是独立目录、最后才补的提交；应该一开始就按任务小步提交。
3. 分类/标签这类"枚举型 UI"，用**一份常量**驱动渲染，别在 HTML 里手写选项
   （这次首页和搜索页的分类入口就是手写的，加一个"生活用品"要改两处）。
